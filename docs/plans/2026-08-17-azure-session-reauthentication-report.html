Implementation plan · 17 August 2026

Azure sessions that recover before users lose their flow.

A complete implementation plan and product mock for proactive Azure CLI session checks, guided browser or device-code reauthentication, multi-tenant visibility, and automatic Kubernetes recovery.

Decision-ready v1.0 Tauri 2 + Rust React 19 + TypeScript No token storage in KubeCLI Estimated: 5–7 engineering days
01 / OUTCOME

What this feature changes

KubeCLI becomes aware of the authentication lifecycle around Azure-backed kubeconfig contexts. It checks silently, explains failures in user language, and coordinates recovery without owning credentials.

Detect early

Check the selected Azure context at startup, after config/context changes, and shortly before the current access token expires.

≤ 10 min

maximum background-check interval while active.

Recover clearly

Replace repeated generic resource errors with one tenant-aware prompt and two clear choices: browser or device code.

1 prompt

deduplicated across concurrent resource failures.

Resume work

After successful login, verify Azure access, refresh namespaces/resources, and restore the action that was blocked.

0 tokens

stored, logged, or returned to the frontend.

Technical truth: Microsoft Entra Conditional Access sign-in frequency is not exposed as a reliable “weekly expiry” timestamp. Proactive behavior therefore means silent token checks and renewal before access-token expiry; the UI prompts only when renewal needs user interaction.

03 / USER FLOW

One guided loop

The same state machine serves startup checks, context changes, scheduled checks, and failures reported by Kubernetes requests.

01Discover

Map current kube context to its kubelogin mode and tenant.

02Check silently

Ask Azure CLI for account metadata and a filtered token-expiry response.

03Explain

Show cluster, tenant, account, and why interaction is needed.

04Authenticate

Browser first; device code is one click away and remains in-app.

05Verify & resume

Recheck session, refresh data, and clear auth-related errors.

04 / ARCHITECTURE

05 / CONTRACTS

Small, explicit domain model

The frontend receives identity metadata and expiry only. Access tokens, refresh tokens, client secrets, and raw Azure CLI JSON are excluded by construction.

StateMeaningUI behaviorNext check
notAzureSelected context is not Azure CLI-backed.Hide Azure control.On context/config change.
checkingStatus command is in progress.Quiet spinner; never block existing terminal work.When command completes.
activeToken acquisition/renewal succeeded.Green compact chip.Earlier of 10 min or expiry − 5 min.
expiringSoonLast known token remains valid, but silent renewal failed.Amber notice; login can be deferred until expiry.Every 60 seconds.
expiredNo usable Azure CLI credential remains.Red chip and guided prompt.After login or manual retry.
signedOutAzure CLI has no matching account/tenant.Friendly “Sign in” action.After login or manual retry.
errorCLI missing, malformed config, or unknown failure.Actionable setup or diagnostics message.Manual retry / environment change.

Frontend contract

export type AzureAuthState =
  | 'notAzure' | 'checking' | 'active'
  | 'expiringSoon' | 'expired'
  | 'signedOut' | 'error';

export interface AzureSessionStatus {
  state: AzureAuthState;
  contextName: string;
  tenantId?: string;
  account?: { username: string; subscriptionId?: string };
  expiresAt?: string;
  affectedContexts: string[];
  reason?: 'interactionRequired' | 'cliMissing' | 'unknown';
  safeMessage?: string;
}

Backend commands and events

check_azure_auth(config_path, context_name)
  -> AzureSessionStatus

start_azure_login(tenant_id, method)
  -> { login_id }

cancel_azure_login(login_id)
  -> ()

event: azure-auth-progress
{ login_id, phase, verification_url?,
  user_code?, safe_message? }

Safe Azure CLI calls

az account list --all \
  --query '[].{id:id,name:name,tenantId:tenantId,user:user,isDefault:isDefault,state:state}' \
  --output json --only-show-errors

az account get-access-token --tenant <tenant-id> \
  --resource https://management.azure.com/ \
  --query '{expiresOn:expiresOn,expires_on:expires_on,tenant:tenant,subscription:subscription}' \
  --output json --only-show-errors

az login --tenant <tenant-id> --allow-no-subscriptions --output none
az login --tenant <tenant-id> --allow-no-subscriptions --use-device-code --output none

The --query projection prevents access-token text from entering KubeCLI’s captured stdout. Process errors are normalized to safe categories before they cross IPC.

08 / RISKS

Known constraints and mitigations

These are product boundaries, not hidden implementation details. The UI should state them clearly when relevant.

No reliable weekly-expiry timestamp

Conditional Access may require interaction without exposing the future deadline. Mitigation: scheduled silent renewal and immediate guided recovery when interaction becomes required.

Azure CLI output varies

Device-code text can vary by CLI version or locale. Mitigation: parse URL/code when possible, retain a safe raw instruction fallback, and test supported CLI versions.

Azure CLI default is global

Changing subscriptions can affect terminals and other KubeCLI windows. Mitigation: explicit confirmation, show current/default subscription, then refresh all windows through polling.

Multiple simultaneous failures

Six parallel resource requests currently fail independently. Mitigation: one auth state transition, one tenant login process, one prompt, and one recovery refresh.

Non-user credentials

Service principals, managed identity, workload identity, and azd are not interactive user sessions. Mitigation: identify login mode and show setup diagnostics instead of an az login prompt.

Browser launch restrictions

Remote desktops and locked-down environments may block browser launch. Mitigation: always expose device code and allow Azure CLI’s own browser-to-device-code fallback.

09 / ACCEPTANCE

Definition of done

A release candidate must satisfy every item below in a packaged desktop build.

  • Azure-backed contexts and tenant IDs are detected from kubeconfig.
  • Non-Azure contexts behave exactly as before.
  • Startup and scheduled checks never expose token content.
  • Browser authentication is the primary recovery action.
  • Device-code instructions, copy, and open-page actions work.
  • Multiple accounts, tenants, subscriptions, and affected clusters are visible.
  • Concurrent failures produce one prompt, not repeated banners.
  • Successful login automatically retries namespaces and resources.
  • RBAC and network failures do not incorrectly request Azure login.
  • Missing Azure CLI produces a setup message with no crash.
  • Login can be canceled and is terminated when the app exits.
  • Automated tests, typecheck, Rust checks, and production build pass.
